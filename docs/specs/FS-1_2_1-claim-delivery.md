## 1. الهدف والنطاق

المحفظة تمسح QR يحمل كود مطالبة، تستبدله مرة واحدة بالوثيقة (SD-JWT + disclosures)،
والخادم يصفّر المادة المشفّرة ذرّياً في اللحظة نفسها. هذا الـ endpoint هو كامل العقد
الخادمي لأول ميزة حقيقية في المحفظة (FS-W0/W1)، وعقد الـ QR المثبَّت هنا هو ما
سيرسمه الكونسول عند الإصدار.

**خارج النطاق:** واجهة المحفظة نفسها، عرض QR في الكونسول (جلسة كونسول لاحقة)،
rate limiting عام للمنصة (هذا الـ spec يضيف كابحاً موضعياً لهذا المسار فقط).

## 2. القرارات D1–D8

| # | القرار | التبرير |
|---|---|---|
| D1 | **`POST /api/v1/claims/redeem`** — الكود في جسم JSON حصراً، لا يظهر أبداً في URL أو query | أسطر access log تلتقط المسارات لا الأجسام؛ كود المطالبة سرّ لمرة واحدة (SEC §9.7) |
| D2 | **ذرّية صارمة بلا نافذة سماح (single-shot)**: في transaction واحدة — قفل الصف (`SELECT … FOR UPDATE`)، تحقق (PENDING + غير منتهٍ)، فكّ تشفير `disclosures_enc`، ضبط `claimed_at`، **تصفير `disclosures_enc`**، صف audit، commit، ثم إرسال الاستجابة. فقدان الاستجابة في الطريق (شبكة الجوال انقطعت بعد الـ commit) = المادة زالت؛ **التعافي = المُصدِر يُصدر كود مطالبة جديداً من الكونسول** (`issueClaimCode` موجود) | «إثباتات لا محتوى»: كل ثانية تبقى فيها المادة قابلة لفكّ التشفير بعد أول تسليم هي مسؤولية بلا مقابل. نافذة السماح كانت ستُبقي المادة حيّة وتضيف حالة وسيطة وعاملاً ماسحاً لها؛ كلفة إعادة الإصدار للجهة الرائدة زهيدة مقارنةً بتعقيد الضمانات. القرار الوحيد في هذا الـ spec الذي يمسّ تجربة الدعم — نقطة النقض الأولى لمجد إن رآها قاسية |
| D3 | البحث بالهاش: الكود المقدَّم ← SHA-256 ← مطابقة `claim_code.code_hash` | FS-0.2: «لا claim code بنص صريح — hashes فقط»؛ الكود نفسه عالي الإنتروبيا فلا حاجة لهاش بطيء (نفس منطق D4 في FS-0.6b) |
| D4 | استجابة النجاح v1 (إضافية-فقط لاحقاً): `{ ref, credential: <compact SD-JWT>, disclosures: [<b64url>…], schema: { id, nameI18n, version }, statusListUri, issuedAt }` — والمحفظة مُلزَمة (يوثَّق في العقد) بالتخزين الفوري قبل أي عرض | كل ما تحتاجه المحفظة للعرض الانتقائي والتحقق دون سؤال ثانٍ؛ `statusListUri` يمهّد لـ KH-1.3 (قد يكون placeholder الحالي حتى تهبط) |
| D5 | **فشل واحد عام**: مجهول/منتهٍ/سبق استلامه/مصفَّر ← نفس `404` بكود **`KH-CLM-0404`** ورسالة واحدة («كود مطالبة غير صالح أو منتهي») بالمفتاح `error.clm.invalid_or_expired` | مضاد سبر: التمييز بين «مجهول» و«سبق استلامه» يسرّب معلومات لماسحٍ خارجي؛ التمييز الحقيقي في audit فقط (نمط D7 في FS-0.6b نفسه) |
| D6 | كابح موضعي: عدّاد Redis بنافذة ثابتة لكل عنوان IP (افتراضياً 10 محاولات/دقيقة) ← `429` بكود **`KH-CLM-0429`** (`error.clm.throttled`) | نفس آلية عدّادات القفل في FS-0.6b؛ يجعل تخمين الأكواد غير اقتصادي دون بنية rate-limiting عامة سابقة لأوانها. `X-Forwarded-For` لا يُقرأ الآن (لا proxy أمامنا محلياً) — يوثَّق كنقطة مراجعة عند تفعيل staging خلف واجهة |
| D7 | Audit: `CLAIM_CODE_REDEEMED` عند النجاح (actor `SYSTEM`، `entity_ref` = ref الوثيقة، لا أي مادة كود). الإخفاقات **لا تُسجَّل فردياً** — فقط `CLAIM_REDEEM_THROTTLED` عند انطلاق الكابح (IP + العدد) | تسجيل كل محاولة فاشلة يحوّل ماسحاً خارجياً إلى مهاجم DoS على جدول الـ audit نفسه؛ الكابح هو الحدث ذو المعنى |
| D8 | **عقد QR v1 يثبَّت الآن** (يوثَّق في README + العقد): محتوى الـ QR نصّ JSON `{"v":1,"api":"<platform base URL>","code":"<claim code>"}` — المحفظة تفكّه وترسل `code` إلى `{api}/api/v1/claims/redeem` | الكونسول يرسم، المحفظة تقرأ، وكلاهما لم يُبنَ بعد — هذه آخر لحظة يُثبَّت فيها العقد مجاناً. `v` يفتح باب التطوير لاحقاً |

## 3. الشكل التنفيذي

- الموقع: `credential/web/ClaimController` + منطق في `CredentialService`/خدمة مخصصة
  `ClaimRedemptionService` (module-private) — لا وحدة جديدة.
- `SecurityConfig`: المسار يُضاف إلى القائمة العامة (المصادقة = حيازة الكود) —
  **القائمة العامة تصبح ثلاثة**: `/api/v1/credentials/verify`، JWKS، وهذا. معفى من
  CSRF (stateless بلا جلسة، نمط `/consume`).
- التنافس مع `ClaimCodeExpiryWorker`: `FOR UPDATE` يحسم أي سباق مع مسح الانتهاء —
  اختبار DoD-4 يثبته.
- config: `khatm.claims.redeem.throttle.max-attempts=10`, `.window=1m`.

## 4. معايير القبول (DoD)

1. المسار السعيد: إصدار → `issueClaimCode` → redeem ← الاستجابة بشكل D4 كاملاً،
   وبعدها مباشرة `disclosures_enc IS NULL` و`claimed_at` مضبوط وصف
   `CLAIM_CODE_REDEEMED` موجود.
2. redeem ثانٍ لنفس الكود ← `404 KH-CLM-0404` (نفس مغلّف كل الأخطاء).
3. كود منتهٍ (أو صفّره الماسح) ← نفس `404` العام — لا تمييز خارجي.
4. **اختبار تنافس**: طلبا redeem متوازيان لنفس الكود ← واحد بالضبط ينجح والآخر
   `404`؛ وسباق redeem مع مسح انتهاء متزامن لا يُنتج لا تسليماً مزدوجاً ولا
   تسليم مادة مصفَّرة.
5. الكابح: المحاولة 11 داخل الدقيقة ← `429 KH-CLM-0429` + صف
   `CLAIM_REDEEM_THROTTLED` واحد؛ بعد النافذة يعود المسار.
6. لا كود مطالبة، لا disclosures، لا مادة مفكوكة في أي لوغ أو صف audit —
   امتداد `NoDisclosureContentInLogsTest` لمسار الـ redeem.
7. المسار عام فعلاً (بلا جلسة/مفتاح) واختبار يثبت أن القائمة العامة = الثلاثة
   المذكورة حصراً (تحديث اختبار D9 القائم).
8. العقد: `docs/api/openapi.json` يتجدد (بوابة `OpenApiContractTest`) والإضافة
   إضافية-فقط (لا مساس بأي مسار قائم)؛ توثيق عقد QR v1 ضمن وصف الـ endpoint.
9. المعتاد (قواعد العمل 1–4): المفتاحان الجديدان في الحزمتين (بوابة المراجعة
   العربية عند الدمج)، Javadoc، `error-codes.md` مولَّد، البناء والـ CI أخضران.

## 5. الأثر

- **عائق `disclosures_enc`: مُغلق نهائياً** (تشفير KH-0.4 ✓، تصفير انتهاء ADR-09 ✓،
  تصفير استلام هنا ✓).
- **FS-W0/W1 (المحفظة)**: عقد QR (D8) + استجابة D4 هما كامل ما تبنى عليه ميزة
  الاستلام؛ لا سؤال مفتوحاً خادمياً.
- **جلسة الكونسول اللاحقة**: عرض QR عند الإصدار يرسم D8 كما هو.
- **KH-1.3**: `statusListUri` في D4 يستبدل placeholder بالقيمة الحقيقية عند هبوطها —
  تغيير قيمة لا شكل، إضافي-فقط.
