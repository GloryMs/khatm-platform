# FS-2.2 — RBAC Granularity & Per-Tenant Operation (KH-2.2.1 → KH-2.2.3)

> **Repos:** khatm-platform + khatm-console · **Status:** APPROVED — 2026-07-28 (نقاط الفيتو الأربع حُسمت بتوصياتها، §4 نهائي — لا تُعاد مناقشتها في الجلسات)
> **Sources of truth:** SEC 21 §7 (سجل الـ scopes + الفصل بين العوالم + 2FA) · FS-0.2 §3.10 (جداول
> app_user/role/user_role القائمة منذ V1، الأدوار الثلاثة المزروعة) · SAD §4.1 (وحدة rbac) · WBS KH-2.2
> **مستوى النموذج:** Sonnet حصراً (rbac وحدة أمنية-حرجة نصاً في SEC §9.3).
> **الجواب المعماري الذي يجيب عنه هذا الـ spec:** المستأجر الجديد قشرة بلا مستخدمين؛ KH-2.2 يمنحه
> مستخدمين وأدواراً، فتعمل كل الشاشات القائمة (schemas، consuming parties، إصدار…) تحت سياقه
> تلقائياً بفضل KH-2.1 — لا حاجة لأي «ربط» يدوي بين مستأجر وschema.

## 1. الهدف

استبدال scope الـ `admin` الخشن (دين مسجَّل من C2b وC5) بسجل scopes حبيبي deny-by-default،
وفتح إدارة مستخدمي المستأجر بحيث يصبح إنشاء مستأجر جديد بداية دورة حياة كاملة قابلة للتشغيل،
لا صفاً في جدول.

## 2. القرارات

| # | القرار |
|---|---|
| D1 | **السجل القانوني للـ scopes** (توفيق SEC §7 الأغنى مع WBS): `issue, verify, consume, revoke, schema:manage, consumer:manage, key:manage, tenant:admin, platform:admin`. (`consumer:manage` إضافة على قائمة SEC — يغطي إدارة الجهات المستهلكة ومفاتيحها، وهو الوعد المسجَّل من KH-1.4.4/KH-2.2.3.) **Deny by default** نصاً: endpoint بلا scope مصرَّح = يفشل اختبار القائمة، لا «يسمح». |
| D2 | **خريطة إعادة البوّابة** — كل endpoint حالياً تحت `admin` يُعاد إعلانه: schemas → `schema:manage`؛ consuming parties + مفاتيحها → `consumer:manage`؛ مفاتيح التوقيع (signing-keys, دوران لاحقاً) → `key:manage`؛ مستخدمو/إعدادات المستأجر → `tenant:admin`؛ سطح `/admin/tenants` العابر للمستأجرين → `platform:admin` حصراً؛ الإصدار/الإبطال/البحث تبقى على scopes الأفعال القائمة (`issue`/`revoke`/…). الخريطة الكاملة endpoint-بـ-endpoint تُنتَج في الجلسة **من قائمة المسارات الحية** (الكود مرجع) وتُرفق بالـ PR body. |
| D3 | **هجرة V10 قطع نظيف لا تعايش**: تعاد كتابة `role.scopes` للأدوار المزروعة — `TENANT_ADMIN` = المجموعة الحبيبية الكاملة عدا `platform:admin`؛ `ISSUER_OPERATOR` = `issue, verify, revoke` (+`schema:manage`؟ لا — قراءة فقط تكفيه، انظر V3)؛ `PLATFORM_ADMIN` = الكل. scope `admin` القديم يُشطب من السجل ومن كل الأدوار — أي جلسة كونسول قائمة تعيد تسجيل الدخول بعد النشر (مقبول في البايلوت، يُذكر في ملاحظات النشر). |
| D4 | **عالم platform-admin والتصرف بالنيابة (on-behalf-of)**: `PLATFORM_ADMIN` يبقى مستخدماً تحت المستأجر الافتراضي (عالم المنصة عملياً — فصل SEC §7 الكامل يكتمل مع 4-eyes في Phase 3)، لكن قراءاته/كتاباته العابرة للمستأجرين لا تتسلل عبر ثغرة: endpoints الـ `platform:admin` التي تمس بيانات مستأجر معيّن تأخذ المستأجر الهدف **صراحة في المسار** (`/api/v1/admin/tenants/{id}/users…`)، وبعد التحقق من `platform:admin` يُضبط سياق المستأجر على الهدف لتلك الـ transaction (نمط SystemAccessExecutor نفسه، wrapper مسمّى `OnBehalfOfExecutor` بقائمة مستدعين معدَّدة ومختبَرة) — **وكل استخدام يُدقَّق** (`AuditAction.ON_BEHALF_OF` + الهدف). |
| D5 | **إدارة مستخدمي المستأجر**: لطاقم المستأجر نفسه (`tenant:admin`): `GET/POST /api/v1/users`، `POST /{id}/roles`، `POST /{id}/lock|unlock|disable`، `POST /{id}/reset-password` (كلمة مؤقتة تُعرض مرة واحدة — نمط plaintext-once المعتمد للمفاتيح؛ تغيير إجباري عند أول دخول). كتالوج الأدوار ثابت (الثلاثة المزروعة لكل مستأجر)؛ أدوار مخصصة خارج النطاق (Phase 4). حارس **آخر-tenant-admin**: لا يُقفل/يُعطَّل/يُجرَّد آخر مستخدم فعّال يحمل `tenant:admin` — 409 بإثبات ذرّي. |
| D6 | **اكتمال الـ onboarding**: `POST /admin/tenants` يقبل اختيارياً `initialAdmin {username, displayName_i18n}` → ينشئ أول `TENANT_ADMIN` بكلمة مؤقتة تُعرض مرة واحدة في الاستجابة. للمستأجرين القائمين: `POST /admin/tenants/{id}/users` (بنمط D4). بهذا يصبح الجواب على «ما بعد إنشاء المستأجر؟»: أنشئه بمديره → سلّم الكلمة المؤقتة → يدخل → ينشئ schemas وجهاته المستهلكة بنفسه. |
| D7 | **الكونسول (C7)**: (أ) إعادة بوّابة كل الشاشات القائمة على الـ scopes الجديدة (`RequireScope` موجود — تتغير القيم فقط) + الـ nav يتبع scopes المستخدم الفعلية؛ (ب) شاشة Users جديدة (لحامل `tenant:admin`): قائمة/إنشاء/أدوار/قفل/إعادة كلمة، بنمط شاشات C2b/C5 حرفياً؛ (ج) تفاصيل المستأجر (C5) تكتسب تبويب Users بالنيابة لحامل `platform:admin` + إدخال `initialAdmin` في نموذج الإنشاء؛ (د) عرض-مرة-واحدة للكلمة المؤقتة بنمط عرض مفتاح API القائم. EN/AR + RTL + بوابة عربية. |
| D8 | **الأخطاء/التدقيق**: `KH-USR-0400/0404/0409` + `KH-USR-0423` (حارس آخر-admin)؛ `AuditAction.USER_{CREATED,ROLES_CHANGED,LOCKED,UNLOCKED,DISABLED,PASSWORD_RESET}` + `ON_BEHALF_OF`. مفاتيح الحزمتين معاً — بوابة عربية. |

## 3. تقسيم الجلسات

| جلسة | المحتوى | ملاحظات |
|---|---|---|
| **KH-2.2a-BE** | D1+D2+D3+D4: السجل، إعادة البوّابة الكاملة، V10، `OnBehalfOfExecutor` | checkpoint داخلي: خريطة D2 كاملة ومختبرة قبل V10؛ اختبار مصفوفي scope×endpoint (كل endpoint يقبل scope-ه المعلن ويرفض غيره — يرث نمط اختبار KH-1.1.3) |
| **KH-2.2b-BE** | D5+D6+D8: سطح المستخدمين، اكتمال الـ onboarding، حارس آخر-admin | `ConcurrentLastAdminTest` (سباق قفلَين متزامنين على آخر أدمنَين → واحد فقط ينجح) ينضم لعائلة اختبارات السباق |
| **C7** | D7 كاملاً | بعد دمج الجلستين؛ preamble: contract:update + self-stop إن غابت أسطح D5/D6 أو بقي `admin` في العقد |
| **دليل الخروج** | e2e حي يجيب سؤال المنتج نصاً: platform-admin ينشئ مستأجراً + مديره الأول → دخول بالكلمة المؤقتة → تغيير إجباري → إنشاء schema تحت مستأجرِه → إصدار → استلام wallet → إنشاء جهة مستهلكة + مفتاح → استهلاك → مستأجر آخر لا يرى شيئاً من كل ذلك | يُسجَّل في STATE |

## 4. نقاط الفيتو

| # | السؤال | الافتراضي المقترح |
|---|---|---|
| V1 | **TOTP 2FA** لحاملي `revoke`/`tenant:admin`/`platform:admin` — SEC §7 يلزم به «Phase 2+». الآن كجلسة ثالثة KH-2.2c-BE، أم يُجدول بنداً مستقلاً قبل خروج Phase 2؟ | جلسة KH-2.2c-BE منفصلة بعد C7 (الالتزام أُطلق الآن؛ تأجيله لآخر المرحلة يخاطر بنسيانه) — لكنها لا تحجب KH-2.3 |
| V2 | `ISSUER_OPERATOR`: هل يرى الـ schemas قراءةً (لاختيار النوع عند الإصدار) بلا `schema:manage`؟ | نعم — نقاط القراءة تحت scopes الأفعال، `schema:manage` للكتابة فقط؛ يُثبَّت في خريطة D2 |
| V3 | القطع النظيف D3 (شطب `admin` كلياً) مقابل إبقائه superset مؤقتاً | القطع النظيف — التعايش يبطل جدوى deny-by-default ويؤجل اكتشاف أخطاء الخريطة |
| V4 | إدارة مفاتيح API من نوع TENANT (سطح KH-1.1 القائم): تحت `tenant:admin` أم `key:manage`؟ | `tenant:admin` — `key:manage` يُحفظ لمفاتيح **التوقيع** حصراً (دوران KH-2.3 قادم عليه) |
