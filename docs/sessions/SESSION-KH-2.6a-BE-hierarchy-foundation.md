## Scope

### D1 — Migration (Flyway، إضافي بحت)
- `parent_tenant_id UUID NULL REFERENCES tenant(id)` + فهرس + CHECK ضد self-parent.
- حارس العمق بحسب قرار §7 المسجَّل (الافتراضي المتوقع: مستويان، فرض خدمة + حارس DB).
- كل الصفوف القائمة تبقى NULL — تحقق صراحةً أن الـ migration يمر على قاعدة staging-like
  ببيانات حية (compose المحلي بعينة بيانات) بلا لمس صف واحد.

### D2 — طبقة الخدمة والقيود
- `TenantService`: إنشاء/تعديل tenant بأب اختياري؛ رفض الحلقات وتجاوز العمق ورفض
  ربط أب معلَّق/محذوف — كود خطأ جديد لعائلة `KH-TEN-042x` لكل حالة، يُضاف إلى
  `docs/error-codes.md` (EN/AR ← **بوابة العربية مفعَّلة هذه الجلسة**).
- حذف/تعليق أب له أبناء نشطون: يُرفض بكود مخصص — لا cascade.
- التدقيق: `TENANT_PARENT_LINKED` / `TENANT_PARENT_UNLINKED` في `AuditAction`.

### D3 — العقد والنَسَب (additive حصراً)
- استجابات إدارة الـ tenant: `parentSlug` + `parentNameI18n` (nullable).
- استجابة التحقق العامة (verify): كتلة نسب اختيارية للجهة المصدرة
  (اسم الأب `name_i18n`) — **بيانات عرضية فقط، لا أثر على منطق التحقق ولا على JWKS**.
  المسار العام يبقى DB-only وfail-open-free كما هو.
- إعادة توليد `openapi.json` + `error-codes.md`؛ بوابة additive-only كالعادة.

### D4 — الاختبارات (أدنى حد)
1. migration على بيانات قائمة: صفر تغيير على الصفوف الحية.
2. حلقة (A←B←A) وself-parent وتجاوز العمق: مرفوضة بأكوادها.
3. رفض حذف/تعليق أب له أبناء.
4. lineage في استجابة verify لابن، وغيابها النظيف لجذر بلا أب.
5. **إثبات الثبات الأمني:** `CrossTenantIsolationTest` يمر **بلا أي تعديل عليه**، وgrep
   صريح في تقرير الجلسة: صفر تغيير في ملفات سياسات RLS.
